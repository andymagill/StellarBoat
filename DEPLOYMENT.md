# StellarBoat Deployment Guide

This document covers deployment for both the canonical StellarBoat demo (Cloudflare Workers with Static Assets) and community forks (Vercel or custom hosts).

---

## Canonical Demo — Cloudflare Workers (Static Assets)

The official StellarBoat demo is deployed to **Cloudflare Workers**, using Workers' native static assets support (the modern replacement for Cloudflare Pages). A `wrangler.jsonc` file in the repo root tells Cloudflare's build system to serve `dist/` as static assets — everything else is handled by Cloudflare's dashboard Git integration, the same low-effort flow Pages used to provide.

### Initial Setup (One Time)

1. **Sign in to Cloudflare Dashboard** — https://dash.cloudflare.com
2. **Navigate to Workers & Pages** — Left sidebar → "Workers & Pages" → "Create" → "Workers" → "Import a repository" (this is "Workers Builds," the Git-integration successor to Pages)
3. **Connect Git**
   - Authorize GitHub
   - Grant access to your repository
4. **Create a project**
   - Repository: select your StellarBoat fork
   - Production branch: `main`
   - Cloudflare reads `wrangler.jsonc` from the repo to know the build output is static assets in `./dist` — no manual build-output configuration needed
5. **Build settings**
   - Build command: `npm run build`
   - Leave all other settings as auto-detected
6. **Environment variables** (if using secrets)
   - Add `PUBLIC_GTM_ID`, `PUBLIC_SITE_URL`, etc. as needed
   - See `.env.example` for all variables
7. **Deploy** — Save settings; Cloudflare builds and deploys automatically from here on

### Deployments

- **Production:** every push to `main` deploys to your main Workers URL
- **Previews:** every PR creates an automatic preview deployment (URL shown in PR)
- **No local CLI deploy step needed** — Cloudflare's dashboard Git integration handles build and deploy directly, same as Pages did

### Form Worker

The site itself is fully static (`output: 'static'` in `astro.config.mjs`, no Astro adapter). The one piece of server-side logic is a hand-written Worker at `worker/index.ts` that handles form submissions — it's wired directly into `wrangler.jsonc` rather than generated by Astro, so the static build and the API route deploy and scale independently.

`wrangler.jsonc`'s `assets.run_worker_first` is scoped to `["/api/*"]`: only requests under `/api/` invoke `worker/index.ts`; every other request is served directly from `dist/` without the Worker running at all.

**Pipeline:** browser → `POST /api/forms` → Worker gates the submission (honeypot, Cloudflare Turnstile, rate limit) → a signed request is forwarded to a Google Apps Script web app → the script appends a row to a Google Sheet and emails a notification. See [ARCHITECTURE.md](ARCHITECTURE.md#form-submission-flow) for the full request/response pipeline and [apps-script/README.md](apps-script/README.md) for the Sheet side.

**Required secrets** (set with `wrangler secret put <NAME>`, or in the Dashboard under your Worker → Settings → Variables & Secrets — **not** as plain vars in `wrangler.jsonc`, which is committed):

| Secret                    | Purpose                                                            |
| ------------------------- | ------------------------------------------------------------------ |
| `TURNSTILE_SECRET_KEY`    | From Cloudflare dashboard → Turnstile → your site                  |
| `APPS_SCRIPT_URL`         | The Apps Script web app's `/exec` URL (see apps-script/README.md)  |
| `APPS_SCRIPT_HMAC_SECRET` | Shared secret; must match the Apps Script's `HMAC_SECRET` property |

Also set the public Turnstile site key as a build-time env var (Dashboard → your Worker → Settings → Variables, or `.env.local` for local builds):

```
PUBLIC_TURNSTILE_SITE_KEY=your-turnstile-site-key
```

**Turnstile setup:** create a widget at https://dash.cloudflare.com → Turnstile, adding both your production domain and your `*.workers.dev` / preview domain as allowed hostnames (a token's hostname must match the request's, or the Worker rejects it — see ARCHITECTURE.md's edge cases).

**Local development** runs two processes together:

```bash
# Terminal 1 — static site with hot reload
npm run dev            # http://localhost:4321

# Terminal 2 — the Worker (needs a build once for the ASSETS binding)
npm run build
npm run dev:worker     # http://localhost:8787
```

`astro.config.mjs` proxies `/api/*` from `astro dev` to `wrangler dev`, so submitting a form at `localhost:4321` reaches the local Worker. Copy `.dev.vars.example` to `.dev.vars` (gitignored) and fill in real secrets, or use Cloudflare's published Turnstile test keys to exercise every gate without a live Turnstile site or Apps Script deployment — see the comments in `.dev.vars.example`.

Regenerate the Worker's binding types after changing `wrangler.jsonc` (new binding, renamed binding, etc.):

```bash
npm run cf-typegen
```

**Porting to another platform:** `worker/forms/handler.ts` is a plain `(Request, FormsEnv) → Promise<Response>` function with no Cloudflare-specific APIs beyond the `FORM_RATE_LIMITER` binding and `request.cf.country` (both easily swapped) — a Vercel or Netlify function can wrap it directly. See the "Forks — Vercel" section below.

### Custom Domain (Optional)

1. Go to your Worker's settings
2. **Domains & Routes** → Add your domain
3. Follow Cloudflare's DNS setup instructions

### Branch Protection (Recommended)

To prevent merging pull requests that fail CI checks:

1. Go to your repository on GitHub
2. Settings → Branches
3. Under "Branch protection rules", click "Add rule"
4. Pattern: `main`
5. Enable:
   - ✓ Require a pull request before merging
   - ✓ Dismiss stale pull request approvals when new commits are pushed
   - ✓ Require status checks to pass before merging
6. Select required status checks:
   - `Lint & Format`
   - `Type Check`
   - `Unit Tests`
   - `Build`
   - `Playwright Tests`
   - `Lighthouse CI`
7. Click "Create"

Now, any PR that fails lint, type-check, build, tests, or Lighthouse will be blocked from merging.

## Forks — Vercel

If you choose to deploy to **Vercel** instead:

### Initial Setup

1. **Sign in to Vercel** — https://vercel.com
2. **New project** → Import Git repo → Select your StellarBoat fork
3. **Framework preset** — Select "Astro"
4. **Build & Output settings**
   - Build command: `npm run build`
   - Output directory: `dist`
5. **Environment variables** — Add via Vercel project settings
6. **Deploy** — Vercel automatically deploys on push to production branch, with preview URLs per PR — same dashboard-driven flow as the Cloudflare setup above

### Porting the Form Worker

Vercel's static output doesn't run `worker/index.ts` — you'll need a Vercel Function (or Netlify Function, etc.) to handle `/api/forms`. `worker/forms/handler.ts` is written as a plain `(Request, FormsEnv) → Promise<Response>` with only two Cloudflare-specific touch points to replace:

- The `FORM_RATE_LIMITER` binding — swap for Vercel's Edge Config, Upstash Redis, or any per-IP counter.
- `request.cf?.country` — swap for your platform's equivalent geo header (e.g. Vercel's `x-vercel-ip-country`), or drop the field from `SubmissionMeta`.

Everything else — schema validation, Turnstile verification, HMAC signing, the Apps Script call — is portable as-is.

### Using vercel.json (Optional)

For custom redirects or edge middleware:

```json
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist"
}
```

## Local Testing Before Deployment

Before pushing to production:

```bash
# Install dependencies
npm install

# Copy example env file and fill in your values
cp .env.example .env.local

# Run dev server locally
npm run dev
# Visit http://localhost:4321

# Test production build locally
npm run build
npm run preview
# Visit http://localhost:3000 (or as shown)

# Lint and type-check before commit
npm run lint
npm run check
npm run check:worker
npm test
npm run test:worker
```

For an occasional sanity check of the exact Workers static-assets config (not required day to day — the dashboard's PR preview URL covers this):

```bash
npm run build
npx wrangler dev
```

## Environment Variables

All build-time environment variables are documented in `.env.example`. Here's a quick reference:

| Variable                    | Purpose                            | Required |
| --------------------------- | ---------------------------------- | -------- |
| `PUBLIC_SITE_URL`           | Full site URL (meta tags, sitemap) | ✅       |
| `PUBLIC_GTM_ID`             | Google Tag Manager container ID    | ❌       |
| `PUBLIC_CONSENT_MODE`       | Enable GTM consent mode v2         | ❌       |
| `PUBLIC_NOINDEX`            | Set robots: noindex for staging    | ❌       |
| `PUBLIC_DEMO_ENABLED`       | Show /demo/\* routes               | ❌       |
| `PUBLIC_TURNSTILE_SITE_KEY` | Turnstile site key (public)        | ❌       |

**Note:** Variables prefixed `PUBLIC_` are visible in browser code; others are private (build-time only). The Worker's secrets (`TURNSTILE_SECRET_KEY`, `APPS_SCRIPT_URL`, `APPS_SCRIPT_HMAC_SECRET`) are **not** build-time env vars — see [Form Worker](#form-worker) above.

## Troubleshooting

### Build Fails on Deploy

Check:

1. Local `npm run build` succeeds
2. All required environment variables are set in platform dashboard
3. Node version is 20+ (check platform's Node version setting)
4. No Git LFS files (StellarBoat doesn't use any, but custom additions might)
5. `wrangler.jsonc` is present and valid (Cloudflare only) — validate locally with `npx wrangler deploy --dry-run`

### Preview Deployment Missing

Ensure:

1. GitHub App is authorized to access your repo
2. Branch protection rules don't block CI status checks
3. Check platform logs (Cloudflare → Workers & Pages → your project → Deployments, Vercel → Deployments)

### Domain Configuration Issues

- **Cloudflare:** Use Cloudflare's DNS or point CNAME to your Worker's default domain
- **Vercel:** Use Vercel's nameservers or point CNAME to `cname.vercel.com`

### Form Submissions Failing

1. **"Verification failed" (403):** the Turnstile widget's hostname doesn't match the request's — add every domain the form is served from (production, `*.workers.dev`, preview URLs) to the Turnstile widget's allowed hostnames in the Cloudflare dashboard.
2. **"JavaScript is required" / redirected to `/form-error?reason=js`:** expected for no-JS visitors — Turnstile can't run without a browser. Confirm the form's `<noscript>` messaging is visible in that case.
3. **"Could not deliver your submission" (502):** the Apps Script `/exec` URL is wrong, the deployment isn't set to **Execute as: Me / Access: Anyone**, or `APPS_SCRIPT_HMAC_SECRET` doesn't match the script's `HMAC_SECRET` Script Property. Run `selfTest()` in the Apps Script editor and compare against the fixed value documented in `apps-script/Code.gs` and `worker/forms/sign.test.ts`.
4. **Rows never appear:** check Workers Observability logs for the Worker's response code, and the Apps Script project's **Executions** log for `doPost` errors.
